# 本地归档流程

## 命名

格式：`YYYYMMDD_HHmmss GPT a-原标题`，B账号使用`GPT b`。

原标题优先读取源素材元数据中的原始标题字段；没有可信标题字段才从文件夹名去掉开头的评/赞/藏计数。不要删标题正文里的日期、人数、天数等数字。Windows非法文件名字符替换为全角或下划线，完整原标题保存在元数据；同秒同名冲突使用workId后缀，不覆盖既有作品。

## 执行顺序

1. 核实本套在线图已生成，取得计划页数及实际图片清单。
2. 在配置的正式成品库创建本套目录，立即写manifest，status=archiving。此时不是完整成品；图片与文案未齐不能进入可发布库存。
3. 经当前账号的有效下载入口逐张保存本套独立成图为P1、P2…，核验文件实际可读、尺寸、哈希、张数与页码对应。网页看起来有图不等于已下载。下载失败保留断点，不把源素材当成成图。
4. 在对应生产会话发送三版本文案提示词并传入独立文案引擎规则，等待回复。三版放在一个text代码块，以COPY_FORMAT:MULTI和VERSION_START/VERSION_END明确分隔，整块一次复制。使用references/three-copy-output-contract.txt合同，不能只取最后一版。复用现有复制/下载扩展，不额外要求搭建面板。
5. 核验三版并使用既有COPY_FORMAT:MULTI合同写入该目录唯一`文案.txt`。已有文件先核对身份、历史和锁，完整替换，不能追加重复三版。
6. 图片、三版TXT与元数据全部齐且验收后，更新manifest status=complete。记录来源、模板、账号、对话链接及耗时，再更新使用次数与生产台账。缺项保持archiving并写明原因。

## 和手动按钮的关系

扩展已有“下载并打包”要求先取文案。用户当前选择先下载图再出文案时，复用底层图片下载能力，最后执行统一归档验收；不先点击要求文案的打包按钮，不以按钮点击成功假报落地。
